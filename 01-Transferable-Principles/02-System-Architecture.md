# 系统架构：把目标组织成可推进的任务

系统架构连接根本目标与具体行动。**方法论先行建立路线，快速反馈、系统一般可用原则和拆分法共同约束路线的设计与调整。**

## 方法论先行：先知道怎样推进

面对陌生项目，直接抓住一个细节持续深挖，容易出现局部有进展、整体却没有推进的情况。开始前需要明确：

- **目标结果**：完成后应得到什么，怎样判断是否达成。
- **关键路线**：哪些环节必须经历，前后如何衔接。
- **主要未知**：哪些问题需要先查证，哪些可以通过试做回答。

方法明确到足以选择下一步，就可以进入实践。无法仅靠分析确定流程时，可以先试做一个代表性案例，再据此调整路线。复杂任务交给 LLM 时，也需要说明目标结果、关键流程和主要不确定性。

## 快速反馈：尽早让判断接触现实

样本不足时，继续优化内部设想，可能只是在反复处理已有信息。**行动时机取决于后果、可逆性，以及问题需要哪种证据。**

| 情况 | 推进方式 |
|---|---|
| 后果难以逆转，或试错代价较高 | 先查清关键约束与风险，再执行 |
| 调整可逆，试错代价较低 | 达到基本要求后，尽早试做并检查效果 |
| 答案主要存在于现实反馈中 | 缩小试验范围，用可承受的成本获取反馈 |

有效反馈应能改变下一步判断。例如，查看一份真实计算输出、跑通一个小样例，能够检验对文件结构和处理流程的理解。试做前明确要验证什么，避免只有动作、没有信息增量。

## 系统一般可用原则：让维护成本与收益相称

**系统能持续带动任务向目标推进，使用负担也可接受时，就不必追求形式上的完善。**

原始记录中的一个例子是：准备重写复刻项目的指令与 README 时，发现当前流程已可正常使用，改写的收益并不明确，因此停止继续优化。由此形成的判断是：修改应回应实际问题。

| 观察到的情况 | 处理方式 |
|---|---|
| 只是表述不够理想，尚未妨碍推进 | 先继续使用 |
| 同类问题反复发生，或明显拖慢任务 | 定位原因，修改对应环节 |
| 规则越来越细，执行和维护都变得繁琐 | 合并或删去低价值规则 |
| 方法已不适合当前目标或条件 | 重新设计相关路线 |

“一般可用”针对工作系统的复杂度与维护投入。科研结论仍须满足相应的证据和检验要求。

## 拆分法：形成局部完整的闭环

宏大目标难以直接执行。**拆分应细化到每一块都有明确目的、可执行动作和可检查的结果，同时保留它与整体的联系。**

一个单元至少需要说清：从哪里开始，完成什么，如何检验，结果交给下一步做什么。复杂单元可以继续拆分；完成后再合起来检查衔接，避免得到许多互不相连的局部结果。

在复刻中，任务围绕相对独立的知识与研究问题组织，使理解、实践和反馈尽量在同一单元内完成。只按代码行序或工作量切段，可能将同一个知识体系拆散，反而增加理解成本。

实际组织方式见 [A 初筛工作流](../04-Learning-Notes/01-Research-Workflow/A初筛（方法论示范）.md)。[C1 2.6](../04-Learning-Notes/02-Stepwise-Learning/C1/C1%202.6处理、对比.md)则围绕数据处理、受控对照与差异分析组织任务，体现了工作流随问题调整的做法。

四种方法需要一起使用：**先形成足以启动的路线，拆出可检验的单元，再用反馈决定继续、调整或停止。** 系统的完善程度以能否支持当前目标为准。
